# 长时间浸泡验证（2026-11-06）

目标：确认前面几项性能改动（事件型通道口径、原生体积接管、脏标记渲染、手动调窗）在
连续运行下是稳态，而不是「启动时好看、十分钟后变慢」。

环境：本机 macOS，`QTRS_NO_RESTORE=1`，内置 MR 样例（`resources/dicom/brain-t1`，256³），
窗口置前，10 分钟，每 30 s 用 `top -l 2 -pid <pid>` 采样（单次采样第一帧恒为 0，取第二帧）。

## 主进程（qt-react-shell）

| 时间 | RSS | CPU | 线程 |
|---|---|---|---|
| 0 min | 537 MB | 57.5% | 40 |
| 2 min | 552 MB | 63.3% | 36 |
| 5 min | 554 MB | 58.1% | 36 |
| 6 min | 526 MB | 6.3% | 35 |
| 8 min | 523 MB | 5.8% | 35 |
| 10 min | 491 MB | 6.0% | 34 |

结论：RSS 先升后降，末值低于启动值，无持续增长；线程数稳定。前 5 分钟 58–63% 的 CPU
只在窗口被反复置前/交互时出现，稳态为 5–6%（波形 canvas 与 Qt 原生条各自刷新）。

## Web 渲染进程（QtWebEngineProcess）

| 时间 | RSS | 备注 |
|---|---|---|
| 冷启动 +30 s | 98 MB | 全新进程 |
| +2.5 min | 241 MB | ≈57 MB/min |
| 浸泡 6.5 min | 704 → 1091 MB | ≈60 MB/min，无平台期 |

内存增长与 JS 堆无关：`QTWEBENGINE_REMOTE_DEBUGGING=9223` 后用 DevTools 协议采样，
`performance.memory.usedJSHeapSize` 恒为 **31.2 MB**，DOM 节点 195、canvas 6 个，均不增长
（`/tmp/heap.mjs`）。停掉前端全部定时器与 `requestAnimationFrame` 后，增长仍在（≈26 MB/min），
CPU 降到 2%，说明是渲染进程的**原生内存**（Chromium/Skia 侧）在涨，不是业务代码持有对象。

## 其它观测

- 看门狗：10 分钟内 0 次「信号中断 / 延迟超预算」。
- 原生体积首帧 356 ms（256³），之后不再重绘（脏标记生效）。
- 心电图/血氧原生条刷新正常，P50 0.23 ms / 0.14 ms。

## 判定

- 主进程：**通过**（无泄漏、无漂移、看门狗无误报）。
- 渲染进程：**不通过**（RSS 线性增长 ≈26–60 MB/min，长时间运行会吃满内存）。
  这是当前唯一阻碍「连续跑一个台次」的问题。

## 已尝试与结论

1. 超声扫描线每帧 `createLinearGradient` → 改为复用单位空间渐变（`sweepGradient` 缓存），
   视觉不变，但增长只从 ≈60 MB/min 降到 ≈26 MB/min，**不是根因**。
2. 关闭所有前端动画后仍在增长，说明与「画多少帧」无关，指向 Chromium 侧的原生分配。

## 归因实验（第二轮）

| 实验 | 做法 | 渲染进程增长 |
|---|---|---|
| 基线 | 正常推流 + 正常绘制 | ≈52–60 MB/min |
| 信号静音 | `QTRS_MUTE_SIGNALS=1`，不向网页转发样本（原生条照常） | ≈10 MB/min |
| 静音 + 停动画 | 再清掉全部定时器与 rAF | **0**（RSS 稳定在 78 MB） |
| 抽稀 1/5 | `QTRS_SAMPLE_DIV=5` | ≈48 MB/min（几乎不变） |
| 抽稀 1/100 | `QTRS_SAMPLE_DIV=100` | ≈16 MB/min |
| ECG 30 fps / 5 fps | 帧限流 | ≈54 MB/min（不变） |
| 神经波形 15 fps | 帧限流 | ≈52 MB/min（不变） |
| 看板 2 Hz→1 Hz | 降刷新 | ≈52 MB/min（不变） |
| 网格 canvas→Path2D | 去掉每帧 canvas→canvas blit | ≈56 MB/min（不变） |
| 软件合成 | `--disable-gpu --disable-gpu-compositing` | 页面空白，实验无效 |

结论：增长与「画多少帧」「重绘用什么方式」都不相关，只在**有数据流进网页**时出现，
且抽稀到 1/5 也不降速；JS 堆恒定（31.2 MB，注意 Chromium 对 `performance.memory` 有量化，
不能作为唯一证据）。根因仍未落到具体分配点（渲染进程 `vmmap` 需要 sudo，未做）。

## 运行期兜底：重建渲染进程

`reload()` 只是重新加载页面，复用同一个渲染进程，实测 RSS 不回落。因此改为**换 profile + 换 page**：
Chromium 会为新的 profile 起一个新渲染进程，旧进程随旧 page/profile 销毁。

- 触发：默认每 30 分钟一次；`QTRS_RELOAD_MIN=N` 改间隔，`QTRS_RELOAD_MIN=0` 关闭。
- 期间原生 ECG/SpO₂ 条与原生体渲染不受影响（它们不经 WebView）。
- 实测：`QTRS_RELOAD_MIN=1` 连续 3 轮，渲染进程 pid 每次都换新，RSS 始终 93–94 MB，
  同时只有一个 `QtWebEngineProcess`；主进程 356 MB；界面数值/三面板/延迟看板全部正常。

`Ctrl+R` / `Cmd+R` 也绑到同一动作，但自动化发键在 Qt WebEngine 里不可靠（键盘事件常被页面吞掉），
验证以日志与进程 pid 为准。

## 下一步（按优先级）

1. 用 DevTools `Memory.getDOMCounters` / heap snapshot 与 `chrome://gpu` 侧内存对比，
   确认是 canvas backing store 还是 IPC/QWebChannel 消息缓冲。
2. 降低数据推送频率（ECG/EEG/EMG 目前 25 Hz，先按显示需要降到 10–15 Hz），
   观察增长是否随消息量等比下降，以区分「渲染」与「传输」。
3. 若确认是 QtWebEngine 原生层，考虑把波形整块迁到 Qt 原生条（已在做），WebView 只留表单类 UI，
   或定期重建 WebView 页面作为兜底。
